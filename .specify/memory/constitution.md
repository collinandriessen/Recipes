# SaaS Corp Constitution

## Core Principles

### I. Stack Discipline
The application is Laravel 13.x + Livewire 4.x on PHP 8.3, using the latest
stable release of each at the time a dependency is added. SQLite is the
local/dev database; production database engine is decided per deployment
target but the app must stay driver-agnostic (no raw SQL that only works on
one engine). Tailwind CSS 4 + Vite is the only frontend build pipeline —
no parallel frontend framework is introduced without an architecture review.
Any proposal to change a pillar of the stack (framework, language runtime,
database engine, deploy target) is an architecture decision and must be
escalated to the Chief of Staff/founder before being adopted.

### II. Spec-Before-Code
No feature-level code is written from a bare prompt. Every non-trivial
feature (anything beyond a one-line bugfix) goes through the SpecDriven
workflow before implementation: `/speckit-specify` → optional
`/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` → optional
`/speckit-analyze` → `/speckit-implement`. Specs live under
`specs/<feature>/` and are version-controlled alongside the code they
describe. A spec captures the "what" and "why" (user stories, acceptance
criteria, constraints) — not implementation detail, which belongs in the
plan.

### III. Scope Boundary (Product vs Engineering)
Product niche and feature scope are owned by the Product Lead and approved
by the founder — Engineering does not invent product scope unilaterally,
including through specs. A spec for a new domain feature is written against
a Product Lead brief or an approved issue; if no such brief exists, Engineering
writes a scope-neutral spec (or flags the gap back to Product) rather than
guessing at the niche.

### IV. Test-First Guardrails
Acceptance criteria in a spec must be translatable into automated tests.
Tests (Pest/PHPUnit) are written alongside — and ideally before —
implementation for the criteria they cover. `./vendor/bin/pint --test` and
`php artisan test` (or `./vendor/bin/phpunit`) must pass before a PR is
opened; CI enforces both on every push/PR to `main`.

### V. Small, Reviewable Slices
Tasks generated by `/speckit-tasks` are scoped to be completable and
reviewable in roughly 1-4 hours and mapped to a single PR where practical.
Large or ambiguous tasks are decomposed further rather than merged as one
sprawling change. Post-merge changes to already-implemented behavior start
by revising the spec, not by patching code directly out of band.

## Technology Stack Requirements

- PHP >= 8.3, Laravel 13.x, Livewire 4.x (latest stable at time of setup).
- SQLite for local dev; production DB TBD per deployment, must remain
  driver-portable.
- Vite + Tailwind CSS 4 for frontend assets.
- Pest/PHPUnit for tests, Laravel Pint (PSR-12) for style.
- GitHub Actions CI: install deps, build assets, migrate, `pint --test`,
  test suite — required to pass before merge.
- New features: Livewire full-page components under `app/Livewire` (or
  single-file Blade components) wired through `routes/web.php`. Avoid
  parallel routing/UI patterns.

## Development Workflow

1. Product Lead / founder approves scope for a feature (issue, brief, or
   explicit go-ahead).
2. Engineering runs `/speckit-specify` to produce `specs/<feature>/spec.md`.
3. Optional `/speckit-clarify` resolves ambiguous edge cases before planning.
4. `/speckit-plan` produces the technical blueprint (architecture, data
   model, API contract) — this is where stack-affecting decisions surface;
   escalate anything that breaks Principle I here, before tasking.
5. `/speckit-tasks` decomposes the plan into small, ordered, testable tasks.
6. Optional `/speckit-analyze` checks spec/plan/tasks consistency before
   implementation starts.
7. `/speckit-implement` executes tasks; each task's tests must pass and
   `pint --test` must be clean before it's considered done.
8. PRs reference the spec they implement; code review checks the diff
   against the spec's acceptance criteria, not just "does it run."

## Governance

This constitution governs how Engineering builds the SaaS Corp product; it
does not grant Engineering authority over product scope (see Principle III).
Amendments are proposed by the Engineering Lead and require Chief of
Staff/founder awareness for changes that affect delivery timelines or the
stack. Individual specs/plans may not silently contradict this document —
a contradiction is a signal to amend the constitution or fix the spec, not
to ignore either.
